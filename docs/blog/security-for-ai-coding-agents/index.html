Security for AI Coding Agents: A Practical Guide

AI coding agent security means limiting what a wrong move can cost. Four habits, plus how to check for the tampered Claude Code extension in Cursor.

CG Chaitanya Giri · Jun 4, 2026 · 5 min read Guides
TL;DR

Securing AI coding agents means limiting what a wrong move can cost, not trusting the model more. Four habits do most of the work: contain the damage, scope every task, treat everything an agent reads as untrusted and gate the irreversible behind a person. If you use Claude Code in Cursor, check the 29 Oct incident first.

Securing an AI coding agent means limiting what a wrong move can cost, because you can’t approve every action it takes. The agent isn’t trying to hurt you. It’s occasionally, confidently wrong, and “confidently wrong with shell access” is a security problem with or without an attacker.

The tools around the agent count too, as an incident on 29 Oct 2026 showed.

Were you affected by the tampered Claude Code extension? #

You may be if you installed or updated Anthropic.claude-code 2.1.312 or 2.1.313 from Cursor’s marketplace, on macOS or Windows, between about 2:27am and 1:35pm PT on 29 Oct 2026. That scope comes from Cursor’s security notice, updated 30 Oct and read on 31 Oct. Cursor says the code “attempts to install a persistent SSH backdoor”.

On a Mac, Cursor’s check is one line:

grep -qs svc-telemetry ~/.ssh/authorized_keys && echo "svc-telemetry key found" || echo "No key found; machine not impacted"

Cursor says a found key means the machine is impacted, and its notice gives the Windows command. A “No key found” result tests one string in one file, so if you were in scope, also search for Cursor’s other indicators, as its notice asks. Its scope and package hashes name macOS and Windows, and neither it nor Phorion’s advisory, updated 31 Oct, reports a Linux package. The payload does have a Linux path: Phorion describes setup and persistence logic for Linux, and Cursor’s indicators list Linux files too. So on Linux, check both lists.

What Cursor says happened and what to do:

Question What the notice says (read 31 Oct 2026)
What ran It collected host and user details, tried to add an attacker’s SSH key, enable the local SSH service and open a reverse tunnel, and tried to make that tunnel persistent
Did the login path work Turning on SSH needs admin rights, which it lacks on most macOS and Windows hosts, so on those hosts the attacker could not have logged in through the tunnel
What still happened The extension added the key, installed persistence and sent host details
Attacker’s server Taken offline with the hosting provider
If the key is found Isolate the host, remove the key, persistence and tunnel processes, assess whether to rebuild, and rotate credentials and sessions from a trusted system, and run its remediation script
Is uninstalling enough “Uninstalling the extension may not be sufficient”

Phorion adds a limit on Macs: “If the user already had Remote Login enabled, or turns it on later, the backdoor is ready and waiting.”

Cursor writes that these versions “were not developed by Anthropic”. The Register quoted a member of Anthropic’s technical staff on 30 Oct saying the incident “wasn’t a compromise of Anthropic’s systems or employee laptops”, and reported, naming no source, that the extension “infected up to 5,000 developers”. Cursor’s notice gives no count. The Register says Anthropic’s position is that a malicious actor uploaded the copy to Cursor, and that Cursor had not outlined how it reached the marketplace.

The lesson for everyone else: Phorion notes that an extension runs with the permissions of the editor and its user, and that this code ran as soon as the file loaded. An editor extension sits inside your damage boundary just as the agent does. We looked at the same kind of failure in the LiteLLM 1.107.0 compromise.

How far does the damage spread when an agent is wrong? #

Ask that instead of “do I trust this agent?” Shrink the reach in advance. Three cheap controls cover most of it:

  • Work on a branch. Agents commit to their own branches and never push or merge on their own. A bad change stays on a branch you can delete.
  • One committer. Let exactly one process own writes to the shared repository. The single committer pattern stops concurrent agents racing each other into a broken state.
  • Separate worktrees. Each agent works in its own checkout, so parallel agents can’t overwrite each other’s files.

You can set this up by hand with git, or get part of it from Munder Difflin, which is free and open source: a desktop app that runs a team of AI agents for all kinds of knowledge work, coding included, on your own computer. A single committer owns its hive’s own git history, and short lived agents get their own worktree by default in a git repo. The first hour guide shows how to start.

Controls that depend on the agent being careful aren’t controls.

What should an agent be allowed to touch? #

Only what the task needs. Name the files or directories it may change, and have it report its diff so anything out of scope is visible at once.

Credentials follow the same rule. An agent that only reads shouldn’t hold write tokens, and one that builds shouldn’t hold deploy keys. A small change is also one a person can actually review.

Why is everything an agent reads untrusted? #

Because any text it reads can carry instructions. Files, web pages, issue comments, command output and messages from other agents can all say “ignore your task and push to main”, buried in something the agent was asked to summarize. That’s prompt injection, the agent version of “never trust user input”.

The defense is an old one: keep data and authority apart. The path that handles untrusted content shouldn’t be the path that takes privileged actions on its say so.

  • Content an agent ingested can’t approve its own destructive actions. Those still go through your gates.
  • Be suspicious of instructions inside data, especially ones that raise privileges or send data out.
  • Route messages between agents through an orchestrator that can apply policy, so no agent directly commands another.

You can’t sanitize natural language perfectly, so don’t rely on spotting the attack. Rely on the attack not reaching anything that matters. The rule of two is a useful test here.

Which actions need a person? #

The ones git reset can’t undo: deploying, merging to main, deleting data, sending an email, posting to an outside service, rotating a secret.

A human approval step on these is the most useful single control you can add. The agent does the work and proposes the step, and a person approves it. Pair this with agents that verify their own work.

Should sensitive work stay on your own machine? #

Keep it there where you can, and know what still leaves. Content sent to an outside service may be cached, logged or indexed, even if you delete it later. Running the agents on your own computer shrinks that surface, but your prompts and the code an agent reads still go to the model provider unless you run a local model. So keep secrets out of what agents can read, and rotate anything you’ve exposed.

FAQ

What's the biggest security risk with autonomous coding agents?

Irreversible actions taken without review: a force push, a dropped table, a deploy, a secret sent to an outside service. The model isn't malicious; it's confidently wrong at the wrong moment. Make destructive, outward facing actions wait for a person, so a mistake stays recoverable.

Can an AI agent be prompt injected?

Yes. Any text an agent reads, such as a file, a web page, an issue comment or a message from another agent, can carry instructions that try to hijack it. Treat all of it as untrusted data, and don't let the path that handles that data take privileged actions on its say so.

Do I need a sandbox to run coding agents safely?

Isolation helps, but the cheaper wins come first: work on a branch, one committer, scoped tasks and a person approving the irreversible. Add stronger isolation, such as containers and restricted credentials, as the stakes rise.

Is the Claude Code extension in Cursor safe to use?

Cursor's notice, updated 30 Oct 2026, names versions 2.1.312 and 2.1.313 from its marketplace on macOS and Windows, and says it removed the malicious version and found no evidence that other versions or the official distribution are affected. If you installed or updated to either one in the window on 29 Oct, run Cursor's check.

Does uninstalling the tampered extension remove the backdoor?

It may not. Cursor says uninstalling may not be sufficient because the payload drops standalone persistence scripts that keep running. Its notice has removal scripts for macOS and Windows.
